# Architecture

OpenTunes is a static web app. Everything runs in the browser: reading the iPod, converting media, writing the database. There is no server component, which is what lets the same app work on a desktop and a phone.

This document describes the target design. Section "What exists" says what is built.

## How a sync works

```
files you pick
   |
   v
probe (codec, bitrate, tags, art)  -->  plan per file: copy / remux / convert / unsupported
   |                                            ^
   |                                            | limits come from the device registry
   v
duplicate check (same judge as planSync): skip what is already on the iPod or repeated
   |
   v
convert in a worker (ffmpeg.wasm, only when the plan says so)
   |
   v
stream files to iPod_Control/Music/Fxx, three at a time  (File System Access)
   |
   v
add track to database with the right media type (libgpod WASM)
   |
   v
back up iTunesDB, write the new one last, re-read it to verify
```

Three at a time is measured, not a guess. On the owner's nano 7G over USB from Chrome on macOS, closing a file costs about a third of a second whatever its size, one file at a time ran at 8.1 and 8.9 MB/s and three at once at 13.2 and 12.3 MB/s in two runs, see [HARDWARE-TESTING.md](HARDWARE-TESTING.md).

Writing the database last means an interrupted sync leaves the iPod with its old, working database plus some unreferenced files, which a cleanup tool can remove. The previous database is backed up before the first write.

## Pieces

**Device identity (WebUSB).** Reads the iPod's serial number and FireWire ID. Newer models sign their database with a checksum that needs the FireWire ID, so a sync cannot be written without it. The ID is the USB serial number. The old TunesReloaded flow read it over WebUSB once and saved it as `FirewireGuid` in `iPod_Control/Device/SysInfo`, which is where the owner's iPod still has it. This app reads that file first and falls back to WebUSB.

**iPod storage (File System Access).** You pick the iPod's root folder. The app streams files into it rather than holding them in memory.

**Database engine (libgpod as WebAssembly).** libgpod parses and writes the iPod's databases, assigns file paths and sets media types. It lives in `engine/` with a C interface of our own and typed bindings, and is built in Docker from pinned sources, see [ENGINE-BUILD.md](ENGINE-BUILD.md).

**Album art (`engine/js/artwork.ts`, `app/src/albumArt.ts`, `app/src/artLookup.ts`).** libgpod cannot write artwork here: it needs gdk-pixbuf, and its ArtworkDB differs from the one a nano 7G has, see [ARTWORK-RESEARCH.md](ARTWORK-RESEARCH.md). So the sync writes the four thumbnails (RGB565, 240, 50, 58 and 57 pixels) and the ArtworkDB itself, shaped like the owner's own unit's file, and only marks each track as having art through the engine (`ot_track_set_artwork`), which libgpod then writes into `iTunesCDB` and the SQLite library. The files are written after the media and before the database, each read back, and put back with everything else if a step fails. The ArtworkDB is added to, never rebuilt: what is in it already is left byte for byte as it is. The app takes a cover from a picture the person chose for that file, else the one inside the file, else `cover.jpg` and its like in the folder, else one found online with the person's approval, by album or, for a file with no album name, by song title ([ART-LOOKUP.md](ART-LOOKUP.md)). Every row of Add music shows which of these it has (`app/src/coverRows.ts`, `CoverRow.tsx`). Whichever cover wins is decoded with the browser's canvas and the pixels are handed over. Photos are not built.

**Backup (`engine/js/backup.ts`).** Copies the iPod's `iTunes`, `Device` and `Artwork` folders and the files directly in `iPod_Control` to a folder the person picks, reads each copy back, and writes a manifest with a SHA-256 per file and a README on how to put them back. It refuses a destination that holds an `iPod_Control` folder. It is the safety net before the first write.

**Rewrite check (`engine/js/rewrite.ts`, `engine/js/sqlite.ts`).** libgpod rebuilds a nano 6G or 7G's SQLite library files (`iTunes Library.itlp/*.itdb`) from its own model of the library, so anything in them that the model does not carry is lost. The check writes the database into the engine's in-memory copy, then compares before and after: the library as libgpod reads it back, every file, and every table and column of the SQLite files (rows, and how many rows hold a value), plus the signatures. A small read-only SQL function in the engine (`ot_sqlite_query_json`) lets it look inside those files. Nothing is written to the iPod.

**Write-back and restore (`engine/js/writeback.ts`).** The first code that changes an iPod, built to be undone. Planning reads the iPod, writes its database in the engine's memory and lists exactly which files would change. Applying refuses to start without a complete backup made in the session, writes the files one at a time (the signed `Locations.itdb.cbk` and `iTunesCDB` last, removals after everything else), reads each back, then reads the whole iPod back with the engine and checks the library and the signatures. If any step fails, every file already touched is put back from the bytes read before the write. Restoring checks every file of a backup against its checksum before writing the first, copies them back one by one and deletes nothing. Only files under `iPod_Control/iTunes` and `iPod_Control/Device` are written; music and artwork never are.

**Offload (`engine/js/offload.ts`).** Copies every media file under `iPod_Control/Music/Fxx` off the iPod as it is, to a new `opentunes-offload-YYYY-MM-DD-HHMM` folder inside one the person picks. The library is read with the engine first (the same way `findOrphans` does), so `library.csv` and `playlists.csv` can name each file. Files are read in 4 MiB pieces, three at once, and each copy is checked by size and by reading it back and comparing a CRC-32 that was computed while the file was read, so the iPod is read once. A file already in the folder with the same size is skipped, which is how a stopped run is resumed. It reads the iPod and writes only the destination, and it deletes nothing: a copy that fails its check is emptied, not removed, so a resume does not take it for a good one.

**Offload folder, backup folder and Restore everything (`engine/js/offload.ts`).** An offload folder holds everything; a backup folder holds only the database files. A backup (`opentunes-backup-...`) is the iPod's `iTunes`, `Device` and `Artwork` folders and the files directly in `iPod_Control`, with `backup-info.json` and no music. An offload folder (`opentunes-offload-...`) holds the media in `F00`, `F01` and so on, `library.csv`, `playlists.csv`, `README.txt`, `opentunes-offload.json`, and a `database/` folder that is a backup folder in exactly the format `backupIpod` writes: the offload calls `backupIpod` into that folder (`BackupOptions.folderName`), reads each file back and checksums it, so nothing is duplicated. It copies the database files the same read-only way as the media. The marker `opentunes-offload.json` holds the format version, the date, whether the copy is complete, the database folder name, the counts of media files and bytes, and each media file's size and CRC-32 (kept from the copy, so a restore can check against it). It has no serial number or FireWire ID of its own, but the saved device files contain them as the iPod holds them, so the README tells the person to keep the folder private. A copy can be partial: `OffloadOptions.include` takes only the files of tracks of some kinds and/or with some track keys (the library, `database/` and the spreadsheets stay complete; a run needs a readable library to do this, and files no track lists are not taken). The marker then carries `partial: { kinds, selectedOnly, tracksInCopy, tracksNotIncluded }` (format version 1, the field is optional), the README begins "PARTIAL copy ... NOT EVERYTHING IS HERE", and `library.csv` gives the tracks left out an empty Path and "not included in this copy" in the File column. `describeOffload` and `restoreOffload` report it ("This copy holds the files for N of M tracks. ..."), and `restoreBackup`, `describeBackup` and `checkBackup` accept a full-copy folder by using its `database/` folder (`resolveBackupFolder`). A stopped run writes a marker marked incomplete; a resumed run saves the (small) database files again and keeps the CRC of files it skips. `restoreOffload` checks the marker and every database file against its checksum before writing anything (`checkBackup`, the same checks `restoreBackup` runs), then copies back each media file the iPod lacks or holds at a different size into `iPod_Control/Music/Fxx` (making a missing `Fxx` folder), in 4 MiB pieces, three at a time. A file whose size already matches is never touched, nothing is deleted, the offload copy is checked against its kept CRC-32 before it is written, and each copy is read back from the iPod and compared by size and CRC-32. Only when every media file is in place does it call `restoreBackup` on `database/`, so the library never lists a file that is not there. A stop works between and inside files; one failed file is reported by name and leaves the database as it was; a stop or failure never starts the database restore. Files libgpod never opens (`iTunesControl`, the radio buffer) are in neither a backup nor an offload, so a wiped iPod does not get them back. The page asks for write permission first, and needs a complete backup of the current state first.

**The Backup tab (`app/src/BackupPanel.tsx`, `LastBackupLine.tsx`, `lastBackup.ts`, `backupChoice.ts`, `selection.ts`, `BackupGate.tsx`).** Step 1 protects the iPod, step 2 puts things back. Step 1 has the last-backup line and one panel. *The last backup:* the page keeps, per iPod folder name, a folder handle to where the last backup was made (IndexedDB, `handles.ts`; written after every successful backup and every finished full copy, the latter as the path of its `database/` folder). When a real iPod folder is opened (`useLastBackup`, run from `IpodViewer` so it does not wait for the tab to be opened) and `queryPermission` says the folder is already granted, `checkLastBackup` verifies it at once with the same checks a restore makes and the same fingerprint comparison of the iPod's library and device files (`backupReuse.ts`). A match counts as the session's backup (chip: "Backup from <date> still matches this iPod"). Without permission there is one button, "Check my last backup", which asks from the click. A missing, damaged, incomplete or other-iPod backup is refused with the reason (a backup whose `SysInfo` or `SysInfoExtended` differs from the iPod's is another iPod's). If the iPod changed since an otherwise good backup, both "Make a new backup" and "Use that old backup anyway" are offered, and the older one counts only after an in-page confirm (chip: "Older backup from <date> in use", and a line in the log). *The panel:* the library is always saved; with nothing ticked it runs `backupIpod`, and with Music, Podcasts, Audiobooks or Video ticked and/or "only the tracks I selected" it runs `offloadIpod` with `include` (the counts shown use the engine's own `includeMatcher`). The Library tab writes its selection to `selection.ts`, which the panel reads. A finished copy's `database/` folder is a complete backup, so it becomes the `BackupReport` the write gate and chip use. *Where a change is off:* `BackupGate` makes the quick backup right there ("Back up now", `quickBackup.ts`), and `writeReady.ts` turns every write button off, with the reason, while a read job holds the lock.

**Folder rules (`app/src/folderRules.ts`).** Pure functions that read a file's folder path inside a chosen folder: which kind the outermost known folder name means, and which tags the folder and file names can fill in. Only tags the file lacks are filled. `addFiles.ts` applies them when a folder is chosen, so the kind becomes the file's `userKind` and the tags reach `SyncItem.info.tags`. The guide people read (`FolderGuide.tsx`) describes the same rules.

**About page (`app/src/About.tsx`, `app/src/credits.ts`).** Reads `THIRD_PARTY.md` and `docs/ENGINE-BUILD.md` into the page at build time and shows each licence as those files state it, so a licence is never typed twice.

**Checksums.** Newer models refuse a database that is not signed. libgpod picks the scheme from the device's own `SysInfoExtended` file and signs the database itself. For the nano 6G and 7G that scheme is hashAB, whose code libgpod does not contain, so the engine compiles the public-domain `dstaley/hashab` implementation in and libgpod calls it directly. Which model needs which scheme is recorded in the registry as each is confirmed.

**Converter (ffmpeg.wasm).** Runs in a worker, only for files that cannot be copied as they are. Single-threaded conversion works everywhere but is slow on a phone, so the planner copies compatible files untouched wherever it can. Multi-threaded conversion needs cross-origin isolation, which the dev server sets and a hosted copy would need headers or a service worker for.

**Device registry (`core/src/devices`).** The single source of truth for what each model can play. The planner and the generated [DEVICE-SUPPORT.md](DEVICE-SUPPORT.md) both read it, so limits are never typed twice. Each row carries a status: `hardware-tested`, `spec-sourced` or `unverified`.

**Demo iPod (OPFS).** A folder in the browser's private storage that stands in for an iPod. It lets the app, and its automated tests, run the whole sync path without hardware.

## Decisions

| Decision | Why |
| --- | --- |
| No backend | One app for desktop and Android, nothing to host or install. |
| Chromium only | WebUSB and folder access exist only in Chromium browsers. Any of them on any OS where the iPod mounts as a drive can work: macOS, Linux and other Unix, ChromeOS, Android (where Chrome offers the folder picker) and Windows (WebUSB may need a driver). Safari, Firefox and iOS cannot reach an iPod this way. |
| libgpod, not a hand-written database | The v1 app wrote a binary iTunesDB by hand with placeholder values. libgpod already knows every model's format. |
| Registry-driven limits | v1 had a hand-typed profile table with no sources, and some rows disagreed with Apple's published limits. |
| Preact and TypeScript | Small, typed, and the app is a handful of screens. One typed worker API replaces v1's three-way iframe bridge. |
| Database written last, with backup | A failed sync must not leave an iPod unusable. |

**AI assistant (`app/src/ai/`, `app/src/AssistantPanel.tsx`).** The one place the page talks to another server, and only after an explicit opt-in. A pure digest (`digest.ts`) turns the library into short numbered lines with no paths; `providers.ts` posts it with `fetch` to Anthropic or an OpenAI-style endpoint with forced tool use; `schema.ts` defines the three tools and validates every answer, dropping what is not allowed. The model proposes only. The ticked proposals become `TrackEdit[]` and `PlaylistChange[]` (`apply.ts`) and go through the same planning, backup gate, read-back and rollback as the Library tab. What is sent and stored is in [AI-ORGANISER.md](AI-ORGANISER.md).

**Duplicates before converting (`engine/js/sync.ts`, `app/src/duplicatePrecheck.ts`, `AddPanel.tsx`).** One judge decides whether a file is already on the iPod or repeats an earlier file in the same list: `createDuplicateJudge` in `sync.ts`, built on `trackFieldsFor`, `identityOf` and `sameItem` (same kind, same normalised artist, album and title, lengths within 2 seconds or one unknown; a file with no usable title is not compared and goes through). `planSync` takes every verdict from it, and `checkDuplicates` runs the same judge over a whole list without preparing anything, so the Add music list can mark each row as soon as the files are read. `itemProblem` is the other shared rule, for files that could never be added. The list is judged again whenever the files, the iPod's tracks (the page passes `snapshot.tracks`), the kind of a file, the "Add files even if..." box or a row's own "Add this one anyway" change, because the marks are worked out from those, not stored. A skipped row is not converted and not copied, and the counts ("9 files will be converted, 3 skipped as duplicates") and the size line leave it out. The order is: check duplicates, convert only what is needed, then `planSync`, which stays the safety net. Both read the same tags: the probe's tags with folder and file name fills, and after a conversion the tags that say which song a file is (title, artist, album, show, season, episode) come from the original only (`mergeConvertedTags` in `addFiles.ts`), so converting cannot change a verdict. The one input that can still differ is the length, which is read from the converted file; the tolerance covers an encoder's padding, and if `planSync` finds a duplicate the first check let through, the page says so. `planSync` also takes `allowDuplicateIds`, so one row can be added anyway while the others are still skipped.

**Find duplicates (`app/src/library/duplicates.ts`, `DuplicatesPanel.tsx`, `app/src/ai/review.ts`).** Pure code groups the same song by the identity helpers in `core` with a length tolerance, keeps live and remix versions apart, recommends one copy to keep by a documented score, and builds the playlist steps that stop a playlist losing a song when its copy goes. Removal reuses `planRemoval` and `applyRemoval` behind the backup gate. An optional AI review sends only the candidate groups and can only change tick boxes.

## What exists

- `core/`: capability detection, song identity, device registry, with tests.
- `app/`: the environment check page with its hands-on probes (USB, folder read and write), and the read-only iPod reader, which loads the engine in the browser, copies an iPod's database files into it, checks the signatures on them and shows what it finds. Demo iPods stand in when there is no hardware.
- `engine/`: a reproducible Docker build of libgpod, a C interface of our own that handles all seven media kinds, playlists and chapters, typed bindings, and tests in Node.

Also built since: offload (copy everything off the iPod), the folder guide and folder-name detection in Add music, the About page, and album art (written and read back in tests, not yet tried on a real iPod). Not built yet: photos and the full library manager. See [ROADMAP.md](ROADMAP.md).
