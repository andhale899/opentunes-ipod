# Changelog

## Unreleased

### One backup panel and an automatic check of the last backup (feature/one-backup)
- **The last backup is checked when an iPod is opened.** The page remembers where it kept the last backup of each iPod folder (by the folder's name, a folder handle in IndexedDB), after every successful backup and every finished full copy. When that iPod is opened again and Chrome already allows the folder, the backup is checked at once: complete, every file's SHA-256, and the iPod's library and device files compared with it. If it matches it counts as this session's backup, the header chip says "Backup from <date> still matches this iPod", and the Backup tab shows one quiet line with "Make a new backup anyway". If Chrome has not given the folder yet there is one button, "Check my last backup". If the backup is missing, damaged, incomplete or another iPod's the page says why. If it is good but the iPod changed since, it says what changed and when the backup was made and offers both "Make a new backup" (the default) and "Use that old backup anyway", which first asks in the page and warns that a restore from it would take the library back to that date; only after the confirm does it count, the chip says "Older backup from <date> in use", and the choice is written to the log. A backup whose iPod identity files (SysInfo, SysInfoExtended) differ from the iPod's is treated as another iPod's and cannot be chosen. This replaces the "Use the backup I made earlier" card.
- **One Backup panel with a media choice.** "Back up the iPod's library" and "Copy everything off the iPod" are one panel with one folder choice. The library is always saved. "Also copy the music and videos" is nothing (the quick backup, as before) or tick boxes for Music, Podcasts, Audiobooks and Video, each with its file count and size from the library the page holds, and, when something is selected in the Library tab, "Only the tracks I selected in the Library tab (N selected)" (the selection is shared through `app/src/selection.ts` and pruned when the library is read again). With nothing ticked it runs `backupIpod` exactly as before; with something ticked it runs `offloadIpod` with a new `include` option (kinds and/or track keys). All four kinds with no selection is the full copy. CSV, README, marker, resume, pause, stop and time left are as before.
- **Partial copies say so.** `opentunes-offload.json` gets an optional `partial` object (which kinds, whether only selected tracks, how many tracks are in the copy and how many were left out; format version unchanged, older readers ignore it). The README starts with "PARTIAL copy ... NOT EVERYTHING IS HERE" and `library.csv` says "not included in this copy" in the File column, with no path, for the tracks left out. A partial copy needs the library to be readable; without it nothing is copied.
- **A finished copy is a backup.** Its `database/` folder is a complete backup, so after a copy finishes the page counts it for the write gate and the header chip and remembers it for the automatic check.
- **Restoring from a full copy.** "Restore from a backup" and `restoreBackup`, `describeBackup` and `checkBackup` accept a full-copy folder (they use its `database/` folder, and the page says that only the library is restored); `resolveBackupFolder` is exported. "Restore everything" shows, for a partial copy, "This copy holds the files for N of M tracks. The other M-N tracks stay as they are on the iPod, or will have no file if the iPod was wiped." in the summary, the confirm and the result.
- **"Back up now" where a change is off.** The notice in Add music, Library, Assistant and Restore everything now has a primary "Back up now" button (folder picker, then the quick library backup, then the chip and the buttons come on with no page change) and a smaller "Backup options" link. If an earlier backup matches it is already counted and the notice does not show. When the last backup needs one click or is out of date the notice says so.
- **Write buttons say why they are off.** While a read job (a backup, a copy, reading the iPod, a check) runs, every button that changes the iPod is off with the line `Off while "<job>" is running. Wait for it or stop it from the bar above.` and comes back on by itself: Put on the iPod, Library edits, removals, playlists, bulk edit, duplicate removal, the AI Apply and its confirm, the restore buttons and the write-back test.
- The Offload tab's old panel and the earlier-backup card are gone; `app/src/BackupPanel.tsx`, `LastBackupLine.tsx`, `lastBackup.ts`, `backupChoice.ts`, `selection.ts`, `quickBackup.ts` and `writeReady.ts` are new. Tests: 13 engine tests (`engine/test/offload-partial.test.mjs`), 29 + 7 app unit tests, 5 new smoke scenarios. Not tried on a real iPod, with a real Chrome permission prompt, or at real USB speed.

### Robustness (hardening/robustness; audit in `docs/audit/robustness.md`)
- A Logs button in the corner opens a drawer of what the app has been doing (jobs started, steps, finished with the time taken, errors, the write note, backup, restore and reconnect). Capped at 500 entries, the last 300 kept across a reload and labelled "before the reload", Errors only, Copy, Download (.txt), Clear, Escape closes. Serial numbers, FireWire IDs and API keys are masked before anything is stored.
- An interrupted-write note kept in the browser (operation, time, iPod folder name, backup folder name; never an ID or a title). If a change never finished, the next page load shows a calm banner with Dismiss and "Take me to Backup".
- One change to the iPod at a time across every panel (and across browser tabs where Web Locks exist): a second write is refused with a plain message, every control is off while a write runs, and a plan is not made while a write runs or a write started while the iPod is being read.
- The activity bar no longer says "Done" for a write that the engine reported as not verified and rolled back.
- The leave-the-page warning now covers every long job. A running job keeps the screen on (Screen Wake Lock, asked for again when the tab comes back), the tab title says it is working, and the bar warns when the tab went to the background.
- "Reconnect <folder>" on the landing page after a reload (the folder handle is kept in IndexedDB). "Use the backup I made earlier" after a reload, only if it passes the restore checks and the iPod's database files still match it exactly (decision in `app/src/backupReuse.ts`).
- "Reload from the iPod" and a "Last read" time in the device header. If the iPod changed outside the page, the screens are reset and the earlier backup stops counting.
- Selections, plans and the playlist view are cleaned up when the library is read again, and a restore now refreshes the library on screen.
- Plain messages when the iPod is unplugged, ejected, locked or full ("The iPod was disconnected. Plug it in, then use Reconnect."), with what was undone when a write hit it. The page checks that the folder still answers every few seconds.
- A global error handler: a small "Something went wrong" notice with a copy-report button (no titles, no IDs) instead of silence.
- The AI assistant's unsent question survives a tab switch and a reload, and after a reload the page says what was cleared.

### Added
- Duplicates are checked before anything is converted (branch `feature/duplicates-before-convert`). The Add music list marks each file as "Skipped: already on the iPod" (naming the matching title and artist) or "Skipped: same as <file name> above", with words and a border style rather than colour alone, as soon as the files are read, and again when the iPod's library changes, the kind of a file changes, or the "Add files even if..." box is ticked or cleared. A skipped file is not converted and not copied; "Check and prepare" shows the count first ("9 files will be converted, 3 skipped as duplicates") and the "can be added, about X MB" line leaves skipped files out. A single row can be added anyway ("Add this one anyway", new `allowDuplicateIds` option of `planSync`) without ticking the box for all. A file with no usable title says "Could not tell if this is already on the iPod (no title)" and goes through, as `planSync` does. The rules live in one place: `createDuplicateJudge`, `checkDuplicates` and `itemProblem` in `engine/js/sync.ts`, used by both `planSync` and the list, so the two cannot disagree (the lookup is also indexed, so a long list against a long library is one lookup per file). After a conversion the tags that say which song a file is come from the original only (`mergeConvertedTags`). If `planSync` still finds a duplicate the first check missed, the page says so. Tested: 24 engine tests that run each case through the pre-check and `planSync` on a real engine, 14 app unit tests, and a headless Chrome scenario on the practice iPod that checks no converter worker starts for a skipped file. Not tried on a real iPod or with a list of thousands of files in the browser.
- Album art for the nano 7G (branch `feature/artwork-photos`). Research first: [docs/ARTWORK-RESEARCH.md](docs/ARTWORK-RESEARCH.md) reads the device file, the owner's backup (an ArtworkDB with one orphaned image and four thumbnail files, sizes and structure only) and public tools, marks each claim confirmed or guessed, and ends with album art GO and photos NO-GO. It corrects an earlier note: libgpod does read `AlbumArt2` and `ImageSpecifications2`. libgpod itself is not used for art, since it needs gdk-pixbuf and writes a different ArtworkDB. `engine/js/artwork.ts` writes the four RGB565 thumbnail files and the ArtworkDB itself, added to an existing file without changing what is in it, reproduces the owner's real ArtworkDB byte for byte from its own fields, and checks the iPod's own description lists the formats first. The engine gained `ot_track_set_artwork`, `ot_track_clear_artwork`, the track's `dbid`, `mhii_link` and `artwork_size`, and keeps the art links of tracks already on the iPod through a rewrite (they were lost before: the ArtworkDB is never read, so every id was 0). The sync writes art after the media and before the database, reads it back, shares one image between tracks with the same picture, leaves a cover off with a warning when it cannot be used, and puts every art file back on a failure. 35 new Node tests, plus unit tests and a headless Chrome scenario for the app side. Not tried on a real iPod.

An opt-in `Find missing album art` step looks albums up in MusicBrainz and the Cover Art Archive with only the artist and album names, shows each picture, and uses none until approved. Privacy and what was learned from the real services in [docs/ART-LOOKUP.md](docs/ART-LOOKUP.md); both services are in `THIRD_PARTY.md` and the About page, which now also says what the two opt-in steps send. - Offload now holds everything needed to put the iPod back. No serial number or FireWire ID is written by the offload itself (the saved device files hold them, as the iPod does, and the README says to keep the folder private). The iPod is only read. A resumed run saves the database files again and keeps the checksums of files it skips. `README.txt` and the page now say what each part is, how to browse (`library.csv`), how to use the audio and video elsewhere, how to put everything back, and how an offload folder differs from a backup folder (a backup holds only the database files). `BackupOptions.folderName` lets a caller name the folder `backupIpod` writes, and `checkBackup` checks a backup without writing.

Stop works between and inside files, a failed file is reported by name and leaves the database untouched, and progress shows files, bytes, speed and a time left. The panel needs a complete backup of the current state first and asks for write permission first in the click. The existing Restore panel recognises an offload folder and points to Restore everything. Tested against in-memory iPods (offload, wipe the music and database, restore, same library and same bytes; a damaged database file refused before any media is written; a stop between and inside files; a failed read and a failed write; a file already there left alone) and in headless Chrome on a practice iPod. ### Changed

- The rewrite check keeps data it would lose apart from empty tables and columns that are merely missing, so the verdict is not padded with differences where nothing was held.

- The nano 7G is recorded as supporting photos and podcasts, because the device declares both. Apple's spec page lists neither.
- Project restructured into `app/`, `core/`, `engine/` and `docs/`, with npm workspaces.
